同一台电脑、同一条线路、同一分钟内，Ookla 测出 480 Mbps，M-Lab NDT7
测出 210 Mbps，校内测速页显示 900 Mbps——**这三个数字可能都是对的**。
它们测的是不同的路径、用的是不同的方法。这篇文章解释造成差异的四个
主要因素。理解它们之后，"数字不一样"就从困惑变成了诊断信息。

## 因素一：单流还是多流

这是方法层面最大的分歧。

**单流**（如 M-Lab NDT7）用一条 TCP 连接做 bulk transfer。它反映的是
"单个连接能跑多快"——这接近单线程下载、单个视频流、一次 `git clone`
的真实体验。单流对 RTT 和丢包非常敏感：一次丢包就会让这一条流降速，
没有其他流补位。

**多流**（如 LibreSpeed 默认三并发、Ookla 通常多连接）同时开多条连接
并把速率相加。它更接近链路的**总容量**：某条流因丢包降速时，其他流会
占住空出的带宽。现代浏览器和下载器普遍并发，所以多流也有其现实对应。

两者没有谁"更真"，它们回答的问题不同：

| | 单流（NDT7） | 多流（LibreSpeed/Ookla） |
| --- | --- | --- |
| 回答的问题 | 单个 TCP 连接的可达吞吐 | 路径的近似总容量 |
| 对丢包/RTT | 敏感 | 相对不敏感 |
| 接近的场景 | 单线程下载、单个流媒体 | 浏览器并发、多线程下载 |

<Warning>
因此 **NDT7 的单流数值与 LibreSpeed/Ookla 的多流数值不可直接横向
排名**。用 210 Mbps（单流）和 480 Mbps（多流）比较大小没有意义；
有意义的是分别跟踪它们随时间的变化。

另外一个常见误解：pace 教育网目标的"三流"是**三个并发 HTTP
请求**，不是三条物理线路，也不表示服务器带宽异常大。
</Warning>

## 因素二：服务器位置与出口路径

测速永远测的是"你到**那台服务器**的路径"。路径不同，瓶颈不同：

- **校内服务器**：流量不出校园网，测的是内网链路，常见几百 Mbps 到
  千兆。这个数字与你访问公网的体验几乎无关。
- **同城运营商服务器**（Ookla 常见的自动选择）：测的是接入网到城域网
  的一小段，往往是所有测法里数字最好看的——因为路径最短。
- **公网/骨干服务器**（M-Lab 由 Locate 服务动态分配）：包含出口、
  骨干甚至国际段，更接近你访问一般互联网服务的路径。
- **特定服务的 CDN**（如 Fast.com 测到 Netflix CDN）：反映的是到该
  服务边缘节点的路径。

IPv4 和 IPv6 也可能走**完全不同的路由**——同一站点两个地址族的结果
差几倍并不罕见，这正是 pace 把它们作为独立目标分别测量的原因。

### 教育网（CERNET）的特殊性

教育网用户对"服务器位置决定结果"的感受最深。CERNET 是独立于三大运营商
的自治网络，校园网到不同目的地至少有三类差异巨大的路径：

1. **校内**：不出校门，速率取决于内网建设，通常很快；
2. **教育网内**（如访问其他高校的测速站）：走 CERNET 骨干，各方向
   容量不均，跨大区可能明显变慢；
3. **教育网出口到运营商/国际**：经由 CERNET 与电信/联通/移动的互联
   出口或国际出口，这些出口是常见瓶颈，高峰期拥塞明显。

同一个宿舍网络，"校内测速 900 Mbps、访问公网视频却缓冲"完全正常——
两个数字描述的是不同的路。此外许多学校对不同路径分别限速，校园 VPN
（如 NJU VPN）又会改变你的出口位置。多视角分别测量，才能定位慢在
哪一段。

## 因素三：TCP 拥塞控制

吞吐数字不只由线路决定，还由两端操作系统的**拥塞控制算法**决定——
它负责回答"现在该发多快"。

- **CUBIC**（[RFC 9438](https://www.rfc-editor.org/rfc/rfc9438)，Linux
  默认）：基于丢包的算法，把丢包当作减速信号。在高 RTT、有随机丢包的
  路径上（比如跨境链路），单流吞吐会被显著压低。
- **BBR**（Google 提出，IETF 拥塞控制工作组标准化推进中）：基于带宽和
  RTT 建模，对随机丢包不那么敏感，同一条路径上常能跑出与 CUBIC 明显
  不同的数字。

测速服务器用什么算法、你的系统用什么算法、路径丢包特征如何，三者共同
决定单流结果。这也是拥塞控制仍是活跃研究领域的原因——IETF 甚至专门
发布了评估新算法的最佳实践
[RFC 9743](https://www.rfc-editor.org/info/rfc9743/)（BCP 133）。对
测速的启示很直接：**不同服务器上测出的单流差异，可能是算法差异而非
线路差异**。

## 因素四：测量口径

即使方法、服务器都相同，实现细节仍会造成百分之十几的出入：

- **时长与预热**：TCP 慢启动需要数秒才到稳态。有的工具剔除前几秒，
  有的取全程平均，有的取峰值区间。
- **统计方式**：平均值、去尾均值还是某个百分位。
- **计量层次**：应用层字节（goodput）还是包含协议头的线路速率。
- **测量时刻**：网络负载分钟级波动，早晚高峰差异可达数倍。

## 结论：让差异成为信息

数字不一样不代表哪个工具在撒谎。合理的用法是：

1. **纵向比较**：同一目标、同一方法、不同时间的趋势才可比；
2. **横向定位**：校内快而公网慢 → 瓶颈在出口；单流慢而多流快 →
   路径可能有丢包或高 RTT；空闲 ping 好而 RPM 低 → bufferbloat；
3. **不要排名**：不同方法的绝对值放在一起排序没有意义。

pace 把每个目标的方法（`librespeed-three-stream`、
`ndt7-single-stream` 等）写进每条结果，就是为了让你始终知道每个数字是
"用什么方法、对哪台服务器"测出来的。下一步：
[如何读懂 pace 的结果](/concepts/reading-results)。
